CompassVPN: итоговый отчёт по четырём вариантам

Дата: 27 октября 2026. Назначение: передача учебного стенда на проверку.

1. Вывод для проверяющего

Развёрнуты три варианта в 3x-ui и отдельный контрольный VLESS REALITY на порту 443. Первые три прошли тест запроса внешнего IP на ПК; пользователь подтвердил их работу через Wi-Fi на Android. Подключение через мобильный Билайн не удалось. Стенд пригоден для демонстрации конфигураций и сравнительного исследования; полное выполнение исходного задания о максимально подходящей хостингу маскировке не доказано.

Это четыре варианта настройки, но три сочетания транспорта/защиты: №04 повторяет стек №01 на другом порту и в отдельной службе. Данных для ранжирования скорости и надёжности недостаточно.

2. Исходное задание и инфраструктура

Задание: развернуть VLESS REALITY в Xray на хостинге, подобрать подходящую этому хостингу маскировку, без self-steal. Дополнительно: подписки, сравнительные проверки, Ansible, Grafana и понятные отчёты.

Фактический VPS: AEZA, Швеция по информации владельца; IP 77.221.138.191, hostname scornful-tan.ptr.network. Геолокация независимо не подтверждалась. Первоначально обсуждавшийся тариф REG.RU здесь не используется.

Наблюдались Ubuntu 26.04, x86_64, 1 vCPU, около 3.8 GiB RAM. 27 октября корневая файловая система: 9.8 GiB, занято 6.0 GiB, свободно 3.3 GiB (65%). Серверное ядро Xray: 26.10.21; тестовое ядро Happ на ПК: 26.7.28, в журнале Android: 26.9.9. Разные версии нужно учитывать при повторении эксперимента.

3. Варианты и обоснование

№01 — VLESS + TCP/RAW + REALITY + Vision, TCP 2443

Базовый вариант панели: простой TCP-транспорт, REALITY, flow xtls-rprx-vision, fingerprint chrome, внешний target/SNI www.google.com. Отдельный порт позволяет параллельно сохранить исходную службу 443. Подходит как контрольная конфигурация для сравнения с XHTTP. Не требует собственного сертификата именно для REALITY-входа.

Ограничение: нестандартный порт может быть недоступен в ограниченной сети; смена fingerprint не обеспечивает доступ к заблокированному IP/порту.

№02 — VLESS + XHTTP + REALITY, TCP 3443

Меняет транспорт на XHTTP с отдельным путём и режимом auto, сохраняя внешний REALITY-target. Вариант нужен для сравнения поведения другого транспорта в тех же условиях и на том же VPS. Это проверка альтернативы, а не доказательство её превосходства. Клиент должен поддерживать используемые параметры XHTTP. Vision flow здесь не используется.

№03 — Hysteria 2 + QUIC/UDP + TLS, UDP 4443

Альтернатива TCP на основе QUIC; позволяет изучать поведение UDP-транспорта. Используется настоящий сертификат для IP, без отключения проверки TLS. UDP должен проходить до VPS. Предполагаемые преимущества на потерях описаны разработчиком, но в этом стенде сравнительные измерения потерь и скорости не проводились. Этот вариант не является VLESS REALITY и сам по себе исходное задание не заменяет.

№04 — VLESS + TCP/RAW + REALITY + Vision, TCP 443

Исходная отдельная systemd-служба Xray; тот же внешний target Google. Контрольный вариант на стандартном HTTPS-порту нужен, чтобы проверить гипотезу «причина только в нестандартных портах». На мобильном подключении он также не заработал: журнал содержит TCP timeouts. Это ослабляет гипотезу о проблеме исключительно портов 2443/3443, но не устанавливает точную причину фильтрации.

№01–03 имеют отдельные URL подписок в 3x-ui. №04 распространялся прямой URI-ссылкой: требование «одна связка — одна подписка» для него пока не реализовано. Доступы и ссылки вынесены из отчёта.

4. Маскировка и соответствие хостингу

В вариантах REALITY используется внешний target www.google.com:443, не собственный сайт на VPS: self-steal не применяется. Однако доступность Google с сервера не доказывает, что target максимально органично соответствует сети AEZA.

Не выполнено сравнительное исследование кандидатов по TLS/ALPN, сетевой близости, стабильности, характерному для адресного пространства HTTPS и поведению при неавторизованном соединении. Поэтому формулировка результата: внешний target настроен, оптимальность выбора для хостинга не подтверждена. Общий SNI с разрешённым сайтом сам по себе не делает IP VPS разрешённым в сети оператора.

В предоставленном error-log обнаружены 16 записей dial tcp 77.221.138.191:443: i/o timeout. В этих попытках сбой возник до обмена REALITY: изменения UUID, SNI или ключей не устраняют недоступность самого TCP-соединения. Сопутствующие DNS-ошибки не объясняют dial timeout к числовому IP.

В subscription-log импорт наших профилей завершался с count=1, lastParseError=null. Промежуточный UnknownContentType одной попытки разбора не следует считать окончательной ошибкой импорта.

Захват пакетов и клиентский журнал не имели подтверждённого общего временного окна. Пакеты от посторонних IP нельзя приписать телефону. Сырые журналы не опубликованы, поскольку содержат частные URL и данные других сервисов.

Сравнение с другим VPN

Предоставленный пользователем рабочий профиль использует VLESS/WebSocket/TLS и правила маршрутизации с DIRECT-исключениями. Заявленный внешний IP отличался от адреса входного сервера. Это может объясняться отдельным выходом или NAT; устройство чужой инфраструктуры не установлено. Копирование SNI из этого профиля не доказывает возможность повторить его доступность на AEZA. Чужие ключи и URL в комплект не включены.

6. Мониторинг и текущая работоспособность

27 октября около 11:14 UTC: Xray active, четыре контейнера запущены, vpn-ip-renew.timer active. Grafana /api/health возвращает database: ok, версия 11.2.0. Prometheus target node имеет health: up, lastError пустой.

Grafana слушает только 127.0.0.1:3000; панель — 127.0.0.1:2053. Внешние входы: TCP 443/2443/3443, UDP 4443. HTTPS-подписки: TCP 2096. SSH: TCP 22.

Дашборд CompassVPN содержит CPU, память, диск, uptime и сетевой график. Сетевой график сейчас относится к namespace контейнера node-exporter (eth0), не к внешнему интерфейсу VPS (net0). Он не подтверждает полный объём VPN-трафика. Метрик по отдельным пользователям, протоколам и успешным VPN-handshake нет. Ресурсные метрики не заменяют клиентские проверки.

Сертификат IP действует с 26 октября 19:25:31 UTC до 2 ноября 11:25:30 UTC. Таймер проверяет продление дважды в сутки с случайной задержкой; активный таймер ещё не доказывает успешное будущее продление. Для standalone ACME должен быть доступен TCP 80. После обновления сертификата перезапускается панель, что может кратко оборвать её соединения.

7. Что не измерялось и что осталось

• Утечки DNS, IPv6 и WebRTC на телефоне и ПК, kill switch, обход туннеля отдельными приложениями.

• Скорость, потери, стабильность длительной сессии, расход батареи и восстановление после смены сети.

• Независимые ПК-тесты без другого активного VPN и сопоставимые повторные прогоны всех четырёх вариантов.

• Успешное подключение через мобильный Билайн и точный механизм ограничения.

• Обоснованный оптимальный REALITY-target для хостинга; четвёртая отдельная подписка.

• Развёртывание всего стенда на чистой машине и оценка уязвимостей используемых версий.

Для повторной проверки фиксировать время UTC, тип сети, профиль, версию клиента, исходный/выходной IP и результат YouTube. Для каждого варианта делать несколько повторов; захват на сервере синхронизировать с журналом телефона. Leak-тесты запускать именно из браузера/устройства под VPN: запрос сайта проверки с VPS утечки клиента не выявляет.

8. Передаваемые материалы и источники

Все playbook и вспомогательный код — в репозитории. Команды PowerShell и порядок эксплуатации — docs/OPERATIONS.md; проверка исходников — docs/VALIDATION.md. Действующие логины, пароли и ссылки — только в локальном private/ACCESS.txt. Приватный SSH-ключ не включён.

Обоснование технических свойств опирается на первичные источники, а не на рейтинг популярности:

• Xray: уровни транспорта и защиты.

• Hysteria 2: QUIC и режимы работы.

• 3x-ui: отдельный сервер подписок, TLS и форматы.

Статус сдачи: комплект для проверки подготовлен с явно перечисленными ограничениями. Успешная работа в мобильной ограниченной сети и оптимальность маскировки не заявляются.
